OVERVIEW

환율과 입금일이 바뀌면 현금흐름은 어떻게 달라질까

수출기업의 계약과 외화 수취 일정을 바탕으로 환율·입금 지연 시나리오의 현금흐름을 분석하는 의사결정 지원 프로토타입입니다. 환율이나 입금일을 바꿔 비교하되, 같은 계약 조건을 넣으면 같은 금액이 나오도록 설계했습니다.

MY SCOPE / TEAM CONTEXT

두 명이 작업했고, 저는 프로젝트를 주도하며 백엔드 계산 엔진과 API를 맡았습니다. 계산은 Decimal 엔진이 맡고 AI는 추출과 설명을 돕도록 설계했습니다. 최종 프로토타입은 문서 추출에 예제 응답을 사용했고, 실제 LLM은 연결하지 않았습니다. 화면과 전체 서비스는 함께 완성한 프로토타입이며 거래 실행 기능은 없습니다.

PROBLEM & CONSTRAINTS

문제와 제약

  1. 확인되지 않은 문서 추출값이 계산에 들어가면 결과의 근거를 설명하기 어렵습니다.
  2. 3주 안에 구현하더라도 계산 공식·반올림 정책·API 계약은 일관돼야 했습니다.

ENGINEERING DECISIONS

계산식과 검산 방법을 먼저 정했습니다

Deterministic financial core

금액 계산은 Decimal 엔진으로

문제

생성형 모델의 응답으로 금융 숫자를 확정할 수 없었습니다.

선택

계산은 Decimal 엔진, AI는 추출·설명 보조라는 경계를 정했습니다.

구현

계산 엔진과 API를 구현하고 미확인 추출값을 계산 입력에서 차단했습니다.

이유

동일한 계약 조건의 결과가 입력 경로와 설명 문장에 흔들리지 않아야 하기 때문입니다.

결과

직접 입력과 확인된 문서 입력의 결과 등가성을 검증하는 구조를 마련했습니다.

범위와 한계

최종 버전에서 문서 추출은 미리 준비한 예제 응답을 사용했습니다. 실제 LLM은 연결하지 않았고 설명 기능은 기본값에서 꺼져 있었습니다.

Independent verification

제품 코드와 별도로 검산

AI 코딩 도구가 만든 구현과 테스트가 같은 오류를 공유할 수 있었습니다.

부분 수취 사례를 대조한 세 경로금융 공식·반올림·API 계약을 먼저 문서화하고 같은 계약 조건으로 결과를 비교했습니다.
검산 경로비교 방법
독립 Decimal 검산제품 계산 코드를 재사용하지 않고 별도로 계산
로컬 API같은 조건으로 실행해 응답을 독립 계산값과 대조
Docker APIDocker에서 실행한 응답을 독립 계산값과 로컬 응답에 대조

구현을 재사용한 계산으로는 같은 오류를 놓칠 수 있습니다. 문서와 코드가 어긋나면 어느 쪽을 고칠지 판단할 근거도 필요했습니다.

확인한 결과

대표 부분 수취 사례의 결과는 세 경로에서 일치했습니다. 별도로 발견한 불일치 항목은 계산 정책에 관한 결정이 필요해, 합의 전까지 검토 대상으로 남겼습니다.

범위와 한계

검산식 작성에도 AI의 도움을 받았습니다. 설계서를 기준으로 계산식을 확인하고 실행 결과를 대조하는 작업은 제가 했습니다.

LIMITATIONS & LESSONS

한계와 배운 점

외부 연동과 데이터 저장

실제 LLM이나 금융 상품 가입 기능은 연결하지 않았습니다. 프로토타입은 데이터를 메모리에 저장합니다.

앞으로 개선할 점

후속 개발에서는 데이터를 서버 재시작 뒤에도 유지하고, 실제 LLM을 연결해 추출값의 출처를 확인할 필요가 있습니다.
