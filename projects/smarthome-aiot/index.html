OVERVIEW

말로 제어하는 스마트홈

일상적인 말로 가전기기를 제어하는 스마트홈입니다. Edge에서 음성을 텍스트로 바꾸면 백엔드가 명령을 해석하고 실행합니다. 등록한 가상 기기 7종의 상태 변화를 3D 화면에서 확인할 수 있습니다.

MY SCOPE / TEAM CONTEXT

네 명이 함께 만든 프로젝트입니다. 저는 AI/NLU와 백엔드를 맡아 자연어를 JSON 명령으로 바꾸고, DB에 등록된 명령 정의로 실행을 검증했습니다. 재질문 상태를 저장하는 DB와 실행 뒤 기기 상태를 갱신하는 백엔드 흐름도 담당했습니다. 팀원은 Edge의 음성 처리, WebSocket 전송, React·Three.js 3D 시뮬레이터를 구현했습니다.

PROBLEM & CONSTRAINTS

해석 결과를 API에 직접 넣어야 했습니다

BEFORE / 초기 구현

Parse → 사람이 JSON 전달 → Execute

AFTER / 개선 흐름

Parse → Clarify / Validate → Execute

  1. 초기 시연에서는 LLM의 parse 결과를 사람이 execute API에 직접 옮겨야 했습니다. 요청과 상태 변경 사이의 수동 단계를 없애야 했습니다.
  2. “청소해 줘”처럼 필요한 정보가 빠진 요청을 임의로 실행할 수 없었습니다. 명령을 보완하는 대화와 종료 조건이 필요했습니다.
  3. LLM이 만든 JSON이라도 허용된 명령이라는 보장은 없습니다. 명령의 존재와 필수값·자료형·범위를 실행 전에 확인해야 했습니다.

ENGINEERING DECISIONS

명령을 해석하고 실행하는 방법

End-to-end command pipeline

명령 해석부터 실행까지 자동으로 연결했습니다

해석 API와 실행 API가 따로 있어서 시연할 때마다 사람이 JSON을 복사해 실행 API에 넣어야 했습니다.

확인한 결과

명령을 직접 옮기지 않아도 device_states와 3D 화면이 갱신되는 것을 확인했습니다.

담당 범위

저는 백엔드의 명령 처리와 DB 갱신을 맡았고, WebSocket 전송과 프론트엔드 화면 반영은 팀원이 맡았습니다.

DB-driven command validation

명령 생성과 검증에 같은 DB 정의 쓰기

문제

LLM이 등록되지 않은 명령이나 범위를 벗어난 값을 만들 수 있었습니다.

선택

commands와 command_parameters를 기준으로 허용할 명령을 정했습니다.

구현

명령 이름, 필수값, 선택지와 범위를 JSON으로 LLM에 전달합니다. 실행 직전 검증 코드에서도 같은 DB 정의와 대조합니다.

이유

모델이 형식에 맞는 JSON을 만들더라도 그 명령을 실행해도 되는지는 코드에서 확인해야 했습니다.

결과

미등록 명령과 범위를 벗어난 값을 실행 전에 걸러냈습니다.

범위와 한계

JSON 명령 형식을 설계할 때 MCP Tool Schema를 참고했습니다. MCP 연동은 구현 범위에 포함하지 않았습니다.

Stateful clarification & error handling

재질문과 취소 처리

문제

답변 도중에 사용자가 취소하거나 다른 기기를 요청하면 이전 명령이 잘못 실행될 수 있었습니다.

선택

session_id로 대화를 구분하고 실행에 필요한 값이 빠진 명령을 MySQL의 dialogue_sessions에 pending_command로 저장했습니다.

구현

후속 답변으로 누락값을 채운 뒤 DB에 등록된 명령 정의를 기준으로 최종 명령을 구성하고, 검증을 통과하면 실행합니다. 취소하거나 다른 기기를 요청하면 이전 명령을 버립니다. 대기 시간은 30초, 재질문은 최대 5회로 제한했습니다.

이유

답이 없거나 요청이 바뀐 뒤에 이전 명령이 실행되는 상황을 막고 싶었습니다.

결과

“에어컨 틀어”처럼 온도가 빠진 요청을 받으면 몇 도로 설정할지 묻습니다. 사용자가 온도를 답하면 그 값을 기존 요청에 채워 최종 명령을 실행합니다.

범위와 한계

대기 명령은 같은 세션의 답변을 받을 때까지 DB에 보관하고, 제한 시간을 넘기면 만료 처리합니다.

Shared interface contract

파트 간 JSON 규격 맞추기

문제

통합 테스트에서 파트별 JSON 형식이 어긋났고, 다음 단계에 필요한 재질문 여부와 차수가 응답에 빠져 있었습니다.

선택

해석 결과와 백엔드 실행, 화면 표시가 같은 응답 규격을 쓰도록 파트별 필드와 상태 갱신 기준을 맞췄습니다.

구현

실행 명령과 응답 문구를 공통 형식에 담고, 재질문 여부와 재질문 차수 필드를 응답에 추가했습니다.

이유

뒤 단계가 재질문 상태를 추정하지 않고 받은 필드로 처리할 수 있어야 했습니다.

결과

음성 입력부터 명령 실행, DB 갱신, 화면 반영까지 팀이 통합 테스트에서 함께 확인했습니다.

범위와 한계

공통 규격은 프로젝트에 등록한 가상 기기와 시뮬레이터의 연동에 적용했습니다.

INPUT / 명령 예시

“거실 에어컨 온도를 22도로 설정해 줘.”

거실 에어컨을 22도로 설정하는 명령의 핵심 필드입니다. 한 문장에 여러 기기 요청이 들어오면 commands 배열에 기기별 명령을 넣고 각각 검증합니다.
{
  "intent": "device_control",
  "commands": [
    {
      "device_name": "living_room_aircon",
      "tool_name": "air_conditioner.set_temperature",
      "parameters": {
        "temperature": 22
      }
    }
  ],
  "clarification_needed": false
}
VERIFICATION & RESULTS

기기 상태와 화면을 대조했습니다

자연어 입력을 예상 JSON과 비교했습니다. 실행 뒤에는 DB에 저장된 기기 상태와 3D 화면이 함께 바뀌는지 확인했습니다.

요구사항 → 시나리오

한 번에 한 기기를 제어하는 경우, 여러 기기를 제어하는 경우, 재질문·취소·복구 상황으로 나눠 테스트했습니다.

입력 → JSON

자연어를 입력한 뒤 JSON의 기기 이름, 명령 이름, 파라미터를 예상값과 비교했습니다. 한 문장에 여러 요청이 들어오면 기기별 명령을 commands 배열로 분리하고 각 항목을 개별 검증한 뒤 실행했습니다.

파트 간 응답 규격

JSON 형식을 맞추고, 추가한 재질문 여부·차수 필드가 다음 단계에 전달되는지 통합 테스트에서 확인했습니다.

JSON → 검증

DB 명령 사전에 없는 이름과 enum·범위 위반의 차단 확인

실행 → 상태

명령을 실행한 뒤 device_states에 예상한 기기 상태가 기록되는지 확인했습니다.

상태 → 화면

WebSocket으로 받은 상태가 3D 화면에 반영되는지 확인했습니다.

세션 → 종료

후속 답변 맥락과 취소·TTL·최대 재질문 조건 확인

OUTCOME

자연어 입력에서 실행과 시뮬레이터 반영까지 수동 전달 없이 연결했습니다.

명령 생성과 검증의 기준을 DB로 통일하고, 정보가 부족한 입력을 재질문 흐름으로 다뤘습니다.

LIMITATIONS & LESSONS

시뮬레이터에서 확인한 범위

모든 입력에 LLM 호출

단순한 반복 명령에도 호출 지연과 API 비용이 발생합니다.

앞으로 개선할 점

자주 쓰는 정형 명령은 규칙으로 처리하고, 복잡한 표현만 LLM으로 넘기는 하이브리드 경로를 검토할 수 있습니다.

기기 상태 캐시

서버를 재시작하면 메모리의 기기 상태 캐시는 초기화되고 DB에 저장된 상태는 유지됩니다.

앞으로 개선할 점

재시작 뒤 캐시와 DB 상태를 다시 맞추는 경로를 검증할 수 있습니다.

등록된 가상 기기 중심

DB에 정의된 기기와 명령 안에서 동작하며 실물 가전의 통신 실패까지 검증한 시스템은 아닙니다.

앞으로 개선할 점

실기기 어댑터, 실패 복구, 명령의 중복 실행 방지에 대한 별도 검증이 필요합니다.

재질문을 넣으면서 답이 없을 때나 사용자가 다른 요청을 했을 때 기존 명령을 언제 버릴지도 정했습니다.
